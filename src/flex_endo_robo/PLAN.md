# Flex endoscope hardware integration

## Starting point

CRF already has a Web UI in `src/app.py`, one camera and YOLO pipeline in `src/scope/`, and UR5 motion over RTDE. The Flex buttons, Flex state, Bird-eye, and Pull Out already exist. The Flex state currently comes from the model in `control_node.py`, and changing it does not move the physical endoscope.

The active Visual Studio target in `tracking_nov` builds `EndoscopeTeleoperation-CRF with self-rotation, pump.cpp`. It drives four tendon axes and one base rotation axis through the GTS controller. Xbox input gates startup and controls both manual movement and the tracking toggle. The top-level `tracking_nov/bottle.py` only displays detection results. The nested `bottle.py` next to the C++ source is the prototype that writes to `EndoVisionShared`. CRF already has a compatible 48-byte writer in `src/scope/yolo.py`, so keep the existing camera worker and model.

The linked GitHub simulation scripts were unavailable during this review. The procedure descriptions below use CRF's checked-in non-ROS port, especially `kinematics.py` and `control_node.py`. Compare the port with the simulation scripts once available, especially the fixed/free frame conventions and the pull-out endpoint. ## Driver and shared memory

1. **Keep the GTS SDK and Xbox setup in the C++ process.** Extract the initialization, paired-tendon moves, base rotation and coordinated rotation, limit checks, and stop operations from the active source. Replace the Xbox-gated main loop and nested button loops with one bounded control loop that can start without a controller. Route Xbox and Web UI input through the same command checks, with one motion owner at a time. Use axes 1/3 and 2/4 for opposing tendon pairs and axis 5 for base rotation. Leave axis 6 (pump) disabled in the first integrated driver. If pump control is brought over later, give it a separate explicit Web UI command with a bounded run and a stop path.
2. **Add a versioned Windows ABI.** Give the C++ project one protocol header and add `flex_endo/flex_ipc.py` as the Python counterpart. Use same-session named mappings for Python-to-driver commands, driver-to-Python status, and Python-to-driver vision. Use new versioned names so legacy publishers cannot feed the new driver. Define fixed-width little-endian fields, magic/version/size, matching C++ size and offset assertions, and a Python layout check. Let the driver create the mappings and the Python client open existing mappings, then validate driver status before accepting commands. Use one writer per mapping and copy each complete snapshot under a named mutex with a bounded wait. A bad header, abandoned lock, repeated read failure or expired heartbeat puts the driver into a stopped state. The prototype's two reads of `seq` before reading the payload leave room for a torn snapshot and do not detect frozen vision. [Microsoft named shared memory](https://learn.microsoft.com/en-us/windows/win32/memory/creating-named-shared-memory)
3. **Separate held intent from one-shot actions.** Commands carry the app/driver session IDs, sequence, heartbeat, requested mode, held jog intent, and one-shot request IDs for calibration and positioning. Keep stop higher priority than any outstanding action. Status carries the driver heartbeat, command acknowledgements and result, active mode and action, calibration state, bend/roll readings with their source, and vendor fault details. Vision carries frame sequence, capture time, target validity/selection, frame dimensions and pixel error. Stop on expired jog or tracking input, driver or app faults, and link loss. Clear old intent on either process restart and require a fresh operator action. Check return codes from the GTS APIs, including initialization and stop, and keep all motion limits in the native loop.
4. **Set up with Xbox and calibrate at rest.** Start the integrated driver uncalibrated after a restart. Let the operator enter local Xbox setup explicitly and use hold-to-jog for tendon bend and base roll within verified setup limits. Stop and clear input on button release, disconnect, or owner change. Once the endoscope is physically straight and aligned to the intended base zero, release the controls and use **Calibrate** in **Flex state** to capture the tendon references (axes 1–4) and roll reference (axis 5) without moving any axis. Require fresh, stationary, fault-free hardware. Calibration ends setup and requires fresh input before motion can resume. Remove automatic startup zeroing and keep tracking and automatic positioning unavailable during setup.
5. **Enforce limits relative to calibration.** Before the first calibration, setup jogging has no software bend cap. After calibration, apply the 60° bend cap relative to the captured zero and retain the first calibration’s travel envelope across re-zeroing. Encoder-backed base roll is limited to ±180° and manual bench roll to ±20° from startup. Use a braking margin for held jogs and keep GTS limit and fault checks active. If only profile position is available, show it as planned travel. **Return to Flex zero** moves the bend axes and base roll to the latest saved zero using the current feedback mode. The driver accepts the return when Flex is idle and **STOP** cancels it.

## Control behavior

- **Manual and fixed/free.** Use the prototype's B/X and A/Y directions for the two bend pairs and its D-pad left/right for axis 5. Verify their signs against the live image and use descriptive Web UI labels. The simulation port's **Free** mode uses horizon-referenced base steering with zero distal compensation. **Fixed** maintains the distal camera horizon as the bending plane changes. Adapt the fixed solution to the available base motor plus coordinated tendon changes, borrowing the prototype's LB/RB coupled movement as an actuator primitive. The prototype exposes only one roll actuator. Verify achievable camera roll across bends on the bench before presenting Fixed as horizon-locked. Stop the active jog before switching modes and use current feedback as the transition reference. The prototype has no variable-arc-length actuator, so omit the model's `R/F (arc)` controls in hardware mode.
- **Tracking prerequisites.** Default off. Require the UR5 to be in active RCM mode with a captured center axis and fresh joint feedback, plus calibrated Flex, a fresh camera stream, and an explicit category. Bottle reproduces the prototype. Recheck these conditions during tracking and stop both tracking outputs if RCM or hardware feedback is lost. Track the selected object's current in-frame detection only. On target loss stop both outputs and show **Waiting for target**. Resume from a fresh in-frame detection, starting with Flex. Manual input, category change, procedure start, Stop, or a stale stream cancels tracking.
- **Flex first, then UR5 rotation.** Keep the arm stationary while the endoscope steers toward the image center. Use the verified camera-to-tendon transform at the current base roll. If a fresh target stays outside the deadband and measured Flex motion approaches its limit in the needed direction, supplement it with bounded UR5 rotation about the captured RCM while maintaining insertion depth. Use the shared 10° half-angle from the captured center axis, checking both measured alignment and each proposed step. Validate the solved pose before issuing a servo command. If the target is still off-center and the remaining correction would exceed the allowable Flex and RCM motion, stop both tracking outputs and show **Tracking limited · target cannot be centered**. Render separate states for Flex following, arm assist, centered, and faults. Use fresh in-frame error for each correction.
- **Bird-eye.** Use fresh UR5 pose and the validated camera mount to compute a downward view with the port's 30° below-horizontal target. Translate the bend plane and magnitude to bounded physical Flex commands and report when the requested view is outside the verified workspace. Complete on fresh feedback at the target, and cancel on stop, manual override, or feedback loss.
- **Pull Out.** Require a captured RCM, fresh UR5 and Flex feedback, and the bench-verified clearance supplied at launch. Return Flex to the latest calibrated zero, confirm straightness visually in planned mode, then align the tube to the captured reference axis while holding depth. Start axial retraction after measured alignment. Use the URDF camera direction to choose the withdrawal sign and measure the straight distal camera's distance from the RCM along the reference axis. Verify the direction and endpoint on the physical mount. Stop both subsystems on stale feedback, failed IK or servo delivery, or motion timeout.
- **Launch.** Build the x86 solution and use `Start-FlexControl.ps1 -FullApp` to start both processes. The Web UI shows offline, connected or faulted state. Launch leaves motion idle and calibration is a separate action.
