# Flex endoscope hardware integration

## Starting point

CRF already has a Web UI in `src/app.py`, one camera and YOLO pipeline in `src/scope/`, and UR5 motion over RTDE. The Flex buttons, Flex state, Bird-eye, and Pull Out already exist. The Flex state currently comes from the model in `control_node.py`, and changing it does not move the physical endoscope.

The active Visual Studio target in `tracking_nov` builds `EndoscopeTeleoperation-CRF with self-rotation, pump.cpp`. It drives four tendon axes and one base rotation axis through the GTS controller. The prototype gates startup and uses a gamepad for manual movement and the tracking toggle. The top-level `tracking_nov/bottle.py` only displays detection results. The nested `bottle.py` next to the C++ source is the prototype that writes to `EndoVisionShared`. CRF already has a compatible 48-byte writer in `src/scope/yolo.py`, so keep the existing camera worker and model.

The linked GitHub simulation scripts were unavailable during this review. The procedure descriptions below use CRF's checked-in non-ROS port, especially `kinematics.py` and `control_node.py`. Compare the port with the simulation scripts once available, especially the fixed/free frame conventions and the pull-out endpoint. [Simulation scripts](https://github.com/YuxuanZhang271/ur5_sim_ws/tree/main/src/ur5_endo_flex/scripts)

## Driver and shared memory

1. **Keep GTS motion in the C++ process.** Initialize GTS and run paired-tendon moves, base rotation, limits, and stops in one native control loop. Web UI commands use one shared-memory motion owner. Use axes 1/3 and 2/4 for opposing tendon pairs and axis 5 for base rotation. Leave axis 6 (pump) disabled in the first integrated driver. If pump control is brought over later, give it a separate explicit Web UI command with a bounded run and a stop path.
2. **Add a versioned Windows ABI.** Give the C++ project one protocol header and add `flex_endo/flex_ipc.py` as the Python counterpart. Use same-session named mappings for Python-to-driver commands, driver-to-Python status, and Python-to-driver vision. Use new versioned names so legacy publishers cannot feed the new driver. Define fixed-width little-endian fields, magic/version/size, matching C++ size and offset assertions, and a Python layout check. Let the driver create the mappings and the Python client open existing mappings, then validate driver status before accepting commands. Use one writer per mapping and copy each complete snapshot under a named mutex with a bounded wait. A bad header, abandoned lock, repeated read failure or expired heartbeat puts the driver into a stopped state. The prototype's two reads of `seq` before reading the payload leave room for a torn snapshot and do not detect frozen vision. [Microsoft named shared memory](https://learn.microsoft.com/en-us/windows/win32/memory/creating-named-shared-memory)
3. **Separate held intent from one-shot actions.** Commands carry the app/driver session IDs, sequence, heartbeat, held jog intent, and one-shot request IDs for calibration and positioning. Keep stop higher priority than any outstanding action. Status carries the driver heartbeat, command acknowledgements and result, active action, calibration state, bend/roll readings with their source, and vendor fault details. Vision carries frame sequence, capture time, target validity/selection, frame dimensions and pixel error. Stop on expired jog or tracking input, driver or app faults, and link loss. Clear old intent on either process restart and require a fresh operator action. Check return codes from the GTS APIs, including initialization and stop, and keep all motion limits in the native loop.
4. **Jog in the Web UI and calibrate at rest.** Start the integrated driver uncalibrated after a restart. Use the Web UI hold-to-jog buttons for tendon bend. Stop and clear input on button release, disconnect, or owner change. Once the endoscope is physically straight and aligned to the intended base zero, release the controls and use **Calibrate** in **Flex state** to capture the tendon references (axes 1–4) and roll reference (axis 5) without moving any axis. Require fresh, stationary, fault-free hardware. Calibration ends setup and requires fresh input before motion can resume. Remove automatic startup zeroing and keep tracking and automatic positioning unavailable during setup.
5. **Enforce limits relative to calibration.** Before the first calibration, setup jogging has no software bend cap. After calibration, apply the 60° bend cap relative to the captured zero and retain the first calibration’s travel envelope across re-zeroing. Encoder-backed base roll is limited to ±180° after calibration. Planned roll is limited to ±20° from startup. Use a braking margin for held jogs and keep GTS limit and fault checks active. If only profile position is available, show it as planned travel. **Return to Flex zero** moves the bend axes and base roll to the latest saved zero using the current feedback mode. The driver accepts the return when Flex is idle and **STOP** cancels it.

## Control behavior

- **Manual control and horizon compensation.** Verify the four Web UI bend directions against the live image. With calibrated Flex and fresh UR5 joints, the base motor and tendon axes work together to compensate for camera roll. Check camera roll with Flex idle, during arm movement, and across the available bend range. The hardware panel exposes the four bend buttons.
- **Tracking prerequisites.** Default off. Require the UR5 to be in active RCM mode with a captured center axis and fresh joint feedback, plus calibrated Flex, a fresh camera stream, and an explicit category. Bottle reproduces the prototype. Recheck these conditions during tracking and stop both tracking outputs if RCM or hardware feedback is lost. Track the selected object's current in-frame detection only. On target loss stop both outputs and show **Waiting for target**. Resume from a fresh in-frame detection, starting with Flex. Manual input, category change, procedure start, Stop, or a stale stream cancels tracking.
- **Flex first, then UR5 rotation.** Keep the arm stationary while the endoscope steers toward the image center. Use the verified camera-to-tendon transform at the current base roll. If a fresh target stays outside the deadband and measured Flex motion approaches its limit in the needed direction, supplement it with bounded UR5 rotation about the captured RCM while maintaining insertion depth. Use the shared 10° half-angle from the captured center axis, checking both measured alignment and each proposed step. Validate the solved pose before issuing a servo command. Use the available correction along the cone boundary when it moves toward the target. If neither actuator can progress, pause both motion outputs, show which limit was reached, and reevaluate fresh observations so tracking can resume automatically. Render separate states for Flex following, arm assist, centered, and faults. Use fresh in-frame error for each correction.
- **Bird-eye.** Use fresh UR5 pose and the validated camera mount to compute a downward view with the port's 30° below-horizontal target. Translate the bend plane and magnitude to bounded physical Flex commands and report when the requested view is outside the verified workspace. Complete on fresh feedback at the target, and cancel on stop, manual override, or feedback loss.
- **Pull Out.** Require a captured RCM, fresh UR5 and Flex feedback, and the bench-verified clearance supplied at launch. Return Flex to the latest calibrated zero, confirm straightness visually in planned mode, then align the tube to the captured reference axis while holding depth. Start axial retraction after measured alignment. Use the URDF camera direction to choose the withdrawal sign and measure the straight distal camera's distance from the RCM along the reference axis. Verify the direction and endpoint on the physical mount. Stop both subsystems on stale feedback, failed IK or servo delivery, or motion timeout.
- **Launch.** Build the x86 solution and use `Start-FlexControl.ps1 -FullApp` to start both processes. The Web UI shows offline, connected or faulted state. Launch leaves motion idle and calibration is a separate action.

## Implementation and verification order

1. Clean the copied Visual Studio project and verify the Win32 SDK build without running the executable. In the integration phase, wire the C++ protocol to a Python fake driver or vendor-free test mode. Check binary layout, one-shot acknowledgements, app/driver restart in either order, stale or invalid input, and disabled controls when the driver is offline.
2. On the bench, verify Web UI setup before calibration, app disconnect, calibration with zero movement, hold/release and focus-loss handling, watchdog stops, hardware feedback, and the ±180° boundary in both directions. Verify that re-zeroing cannot bypass tighter mechanical limits.
3. Verify automatic correction against visible camera roll through the supported bend range. Exercise Bird-eye and Pull Out with logged commands and simulated feedback first. On the bench, verify physical straightness before retraction, signed withdrawal and endpoint, and cancellation mid-procedure. Check that **STOP** reaches both motion controllers and closes the session.
4. Exercise tracking with recorded frames and then the live camera. Verify RCM entry and pivot motion, Flex-only following inside its range, arm assist near the Flex limit, the 10° boundary in combined tilt directions, the Web UI limit indication, target loss, and frozen streams.
